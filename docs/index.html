01 — The problem we solve

Smart assistants, terrible time management

Ask an AI: "Compare these three system designs from the attached documents and tell me which is strongest." Three things routinely go wrong:

🛑 Quitting too early

The answer sounds confident but never read the third document. Nobody notices — it looks finished.

🔁 Rambling too long

The answer was solid after 3 searches, but the assistant does 12 more "just to be thorough" — burning time, money, and your patience.

🧭 Wrong direction

All the evidence sits in a different set of documents, but the assistant keeps re-phrasing the same failed search instead of pivoting.

Today's fixes are crude: max_tokens, "be thorough but concise", a fixed number of searches. None can tell done apart from stuck apart from blocked. That distinction is what this project adds.

02 — The idea

An assistant, a manager, and a checklist

👩‍💻 The worker

Reads documents, searches, drafts the answer. Great at research — bad at judging when to stop. Like most of us.

🧑‍💼 The controller

Never touches the research. Writes a contract (what "done" means), hands out small leases ("3 searches toward this gap, then report back"), checks work at checkpoints.

✅ The gate

Finishing needs every box ticked: draft exists, required reading done, claims evidenced, format right, nothing blocked. One box unchecked = no finish.

The golden rule: finishing is about the checklist — never "I feel done" or "I've searched enough." Effort calls (keep going? verify? pivot?) use cheap signals plus a cost–benefit score, and can never override the checklist.
03 — How it works

Five steps, every single run

  1. Write the contract. Goal, must-do steps ("read all three designs"), claims needing evidence, answer format. → contracts.py
  2. Grant a lease. Up to 3 actions toward one gap. SHORT (1), STANDARD (3), EXTENDED (5) — permission for one intent, never a blank cheque. → leases.py
  3. Worker acts; everything is logged. Each search lands in an immutable trace with its cost. Facts first, interpretation later. → trace.py
  4. Checkpoints fire on events only — finish requested, lease expired, repeats with nothing new, contradiction, tight budget. Not after every step (the expensive mistake others make). → guards.py
  5. Checklist first, effort second. All boxes pass → ALLOW_FINALIZE. Else rank keep-going / double-check / pivot by value per cost and grant the next lease. Nothing viable? Ask the user, or report blocked — an honest "I can't finish", never disguised as success. → controller.py scoring.py gates.py
🔍 Spotting "stuck", cheaply: if the last p searches look near-identical (J ≥ tau_J) and bring almost nothing new (UPR ≤ tau_U), the lease ends and a checkpoint inspects. That signal means "look closer" — never "we're done". → stagnation.py

06 — Proof, not promises

How we'd know if this is wrong

The design states its own kill criteria — if any turn out true, the controller isn't earning its keep:

  • A plain "be thorough" prompt or fixed search budget matches it on quality.
  • The controller's own cost eats the time/money it saves.
  • Unsupported or premature answers increase.
  • Pivoting never beats "just search more in the same place".

Planned ladder: uncontrolled worker → fixed-shallow / fixed-deep → generic prompt → fixed checkpoints → CGLC without stall detection → CGLC without scoring → full CGLC. Scored on correctness, checklist compliance, evidence grounding, user time, system cost, and controller mistakes. → src/cglc/evaluate/ · pytest -q (18 tests green).
